# Redis write-path batching

This change follows the final wire/media validation and omitted-metadata response correction. Those earlier image results are preserved independently; no Docker application images or benchmark measurements were produced for this optimization.

Read-only source evidence found the normal message callback awaiting room publication and each member unread publication separately. The benchmark HQ fixture has six members, producing seven Redis publication exchanges. Durable enqueue additionally awaited SADD and RPUSH separately. The final path needs one ordered publication Lua loop (seven PUBLISH operations) and one durable enqueue Lua exchange. This reduces the source-level exchange count from nine to two; it is not a measured throughput or latency improvement.

The generic `RedisTransport.IntegersAsync` accepts1–64 commands. A borrowed connection writes/flushed the complete batch before reading each reply in order, authenticates/selects only on socket creation, and is returned only after all replies are consumed. Errors/cancellation dispose it without replay. Application publications use `PublishBatchAsync` instead: a bounded1–64-PUBLISH Lua loop with `redis.call`, which stops at the first server-side error. Large room broadcasts use successive bounded64-operation chunks, preserving publication order. The original room/member stream names, payloads and receiver permission checks are preserved; room type and serialized unread payload are reused within the callback.

Redis pipelines are not atomic: commands after a server-side error may already have applied. This differs from the original sequential client, which stops sending after the first error. Valid default-ACL PUBLISH commands pass; a custom channel ACL can cause a middle publication to fail while a later permitted member publication still happens. No universal error-boundary parity, rollback or retry is claimed. Durable enqueue therefore uses Lua with registration before append; a registration wrong-type/permission failure cannot append the job. Original Resque wrapper, queue ownership, leases, retries and disabled-outbound holding remain intact. No durable jobs were replaced with losable process queues.

An actual local Redis7 custom-ACL check is preserved in `redis-acl-boundary.json` and reproduced by `bench/parity/realtime_media/redis_acl_boundary.py`. The first and third channels are allowed; the middle channel is forbidden. A subscriber captures first only for sequential sends and a Lua `redis.call('PUBLISH',...)` loop, but first plus third for a generic RESP pipeline. All three surface the permission error. An administrative sentinel establishes the capture boundary without idle-time assumptions. Parent approved the Lua publication loop to preserve the sequential stop-at-first-server-error behavior while retaining already-applied prefix effects and using one exchange. It is implemented and the same controlled ACL case passes against the concrete production `PublishBatchAsync`, not only a hand-written harness script. EVAL permission is needed (already required for durable jobs/rate limiting); an installation that permits PUBLISH but forbids EVAL needs an ACL change. The generic pipeline API intentionally keeps Redis's native non-atomic error behavior and never replays uncertain writes. Lua does not roll back prior publications on error, and an uncertain script acknowledgement is never automatically retried.

Actual focused verification ran on Linux with Redis7 and server CPUs16–19:

```text
docker run --rm --cpuset-cpus 16-19 -v A:/External/minimal-api-benchmark:/work -v C:/Users/Vaclav/.nuget/packages:/packages -e NUGET_PACKAGES=/packages -e CAMPFIRE_TEST_REDIS_URL=redis://host.docker.internal:46379/15 -w /work mcr.microsoft.com/dotnet/sdk:10.0 dotnet run --project tests/Realtime/Realtime.Tests.csproj -c Release --artifacts-path /tmp/artifacts
```

Exit0; all three console groups passed:

- Original Action Cable frames, guarded membership streams, DOM/scroll/remove callbacks, presence and revocation/replay.
- Pooled reply isolation/reuse and bounds;64 concurrent three-command batches return1/2/3 in order. Cancellation after INCR preserves one applied write and reconnects. A middle command error leaves two increments applied, surfaces failure and never reuses unread replies.
- Fake peer withholds replies until both batch writes arrive, acknowledges the first and drops the second: exactly two batch writes apply, no replay occurs, and the next connection authenticates/selects once. A65-command batch fails before network writes.
- Concrete publication Lua with a forbidden middle channel delivers only the allowed prefix. A fake peer applies both Lua publications and loses the script reply: the caller fails, no publication is replayed, and the next healthy connection is reusable.
- Two independent app hosts preserve room-before-user-unread delivery and deleted-message UUID removal. Durable registration wrong-type failure leaves the ready list empty. Existing shared disconnect, fixed-window Lua counter, held outbound/internal independence, original malformed job failure, exact retry and expired-worker recovery controls still pass.

No benchmark speedup is claimed here.
