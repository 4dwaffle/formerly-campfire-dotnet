# Identity and persistence Rails parity audit

Full parity is **not verified and is contradicted by the differential checks below**. Happy-path functionality, source-generated SQL and successful existing tests do not establish the complete Rails contract. No production fixes were made during this audit.

Audit date: 2026-10-05. Rails source: `upstream` commit `6c7f8fa15f8c39478af64a483dcdf6223527ed22`. Its Rails framework is pinned by `upstream/Gemfile.lock:35` to `1a02651ac37fb64b4de2a2b73461d86acf9c98fb` (8.2.0.alpha). Live reference image: `ghcr.io/basecamp/once-campfire@sha256:7197fff46e15d0dce69e0a16624df239e1b9bd069534dc28dec67ab7b6771672`.

JIT image ID: `sha256:3a55c45da1ea7be371ec92334c326565d9f79921d9381dcea3a71f18c3062545`. AOT image ID: `sha256:8195ed259a53e8904c561b5cdc6ece0f962b0bb53744d906386b83d79185c620`. The same pinned seed, secret and environment were used, in separate disposable Docker volumes. Outbound hooks/subscriptions were removed before cloning. Hook fixtures use `127.0.0.1:9` and are deleted before content mutations. No external contacts occurred.

## Evidence and reproducibility

- [check.py](check.py): 39 named HTTP cases per implementation, comparing actual status, normalized redirect and content type; selected SQL snapshots compare persisted side effects. **110 field differences** across JIT/AOT, including multiple fields for one underlying issue. This number is not a count of independent bugs.
- [edges.py](edges.py): 12 named non-CSRF-setup cases per implementation; real transfer links, parameter errors, browser/user-card HTML, semantic profile controls, ban callbacks; six directional cookie/session interop checks. Existing authentication rows are explicitly copied between disposable databases so cookie verification is exercised against the corresponding persisted token.
- [fresh.py](fresh.py): additional independently generated/cleaned Rails/JIT/AOT families; malformed and normal first-run requests, table/foreign-key metadata, migration metadata, and pinned Rails `db:migrate:status` against newly created .NET databases. `db:prepare` was deliberately not run on the .NET-created database because migration replay can destroy data.
- [decrypt_cookies.rb](decrypt_cookies.rb): pinned Rails' actual `ActiveSupport::MessageEncryptor` reads captured browser cookies. Shows failure with normal URI decoding and success with an extra decode.
- [culture parity probe](../../../tests/Parity/Identity/Culture/Program.cs): uses the production `RailsCrypto` and a vendored Rails expiring signed-cookie golden vector under five cultures. **3 matched; 2 failed** (`th-TH`, `ar-SA`). It is an intentional failing parity probe, not a production fix.

Run HTTP scripts with standard Python on a **fresh disposable identity family** generated by the parent and recorded in `runtime/instances.json`:

```text
python bench/parity/identity/check.py
python bench/parity/identity/edges.py
python bench/parity/identity/fresh.py
dotnet run --project tests/Parity/Identity/Culture/Culture.csproj -c Release
```

Scripts return 1 for parity differences, 2 for harness failures. `check.py` changes the Rails member's password in the long-password case; do not reuse a previously mutated family as a fresh baseline. Login attempts also consume real rate-limit slots. Raw HTML, headers, cookies and DB snapshots are ignored under `runtime/`; these are test credentials and should remain local. Initial interop diagnostics selected a later transfer-created session instead of the source cookie's row; that harness mistake was corrected before recording the confirmed interop finding.

## Existing test evidence and its limits

The owned identity suite currently contains 13 tests in `tests/Identity/IdentityTests.cs` (methods start at lines 17, 42, 57, 68, 82, 93, 102, 125, 143, 163, 186, 196, 207). Parent's wider aggregate suite passing does not replace Rails differentials. The source-linked identity host uses fake page/media/realtime services; it checks requested side effects, not real DOM/controller interactions, disk transformations, remote disconnect failures or Rails reverse cookie decoding.

Strong existing checks include: signed/encrypted primitive verifier vectors; purpose/expiry and legacy Marshal string SGIDs; CSRF token math; SQL generated mappings/list handling; immediate rollback/FKs/WAL; ordinary first run/login/admin permission/deactivation; normal bot lifecycle; ban captured blob/client IDs; settings/invitation/profile field allowlists; per-request auth cache and fresh-session read-only behavior. New probes expose gaps precisely because they cover missing inputs, alternate HTTP formats, locale calendars, framework behavior and Rails rollback.

Confirmed matching runtime slices: normal fresh signup creates Campfire / one administrator / one room / one membership / one session; invited members receive all open-room memberships; member account mutation and bot administration are forbidden; invalid role falls back to member; deactivation rewrites email and removes sessions/shared memberships; valid/invalid generated transfer statuses match; ordinary logout and ensuing protected redirect match; missing-token and wrong-Origin rejection status match; fresh table column/FK structures and index names match. These are bounded findings, not a full-parity declaration.

Unverified areas remain explicitly listed above. Authentication wire-cookie rollback, migration metadata, ignored JSON and missing original profile controls are blockers before any claim that the port can transparently replace and roll back to pinned Rails.
