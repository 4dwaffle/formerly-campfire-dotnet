The original [audit](report.md), [134 selected baseline assertions](assertions.json), source inventory and raw captures remain unchanged. This report records fixes against pinned Rails `6c7f8fa15f8c39478af64a483dcdf6223527ed22`; it does not certify every possible rich-text or browser state.

## Search callback durability proof

The source uses `after_create_commit`, `after_update_commit` and `after_destroy_commit` in `Message::Searchable`. A temporary populated ordinary table replaces FTS only during the isolated fault probe because SQLite virtual tables cannot have ordinary abort triggers. The original virtual table is restored in `finally`, and every fixture change is recorded.

[Before-fix captures](runtime/remediation-fts-before/summary.json) demonstrate all three requests returning 500. Rails retains the created message with no index entry, retains an updated body with its old index text, and retains deletion with an orphaned index entry. The room touch commits; the later unread receive callback does not run after indexing raises. JIT/AOT previously rolled the whole message transaction back. A separate [Rails boost fault](runtime/remediation-boost-fault-before/rails/responses.json) proves that `Boost`'s touched message also runs the after-update index callback: the boost remains committed despite 500.

A further controlled open-room grant failure demonstrates that Rails keeps the room and creator membership when its after-save bulk grant fails; the port now has the same callback boundary. The port now commits message/rich-text/attachment/room changes before raw index callbacks; create's unread callback follows successful indexing. Index updates use UPDATE, preserving Rails' behavior when an index row is absent. Message and room deletion remove index rows after the primary transaction; boost create/delete touch and commit before the index callback. Invalid attachments still fail inside the initial transaction and roll back message/unread/room changes.

### Confirmed cache-policy difference and source correction

The additional [production cache probe](cache-policy-final-03.json) confirms `perform_caching=true`, `ActiveSupport::Cache::RedisCacheStore` and a successful local cache roundtrip in pinned Rails. After warming a newly created message, changing its creator name/user version while leaving the message version unchanged still displays the old creator in Rails. Editing its raw body to the same length without changing rich-text/message timestamps also displays the old body. The intermediate JIT/AOT images displayed both changes immediately. Model ETags remained unchanged within each application; their newly created timestamps differ across applications, so this probe does not assert cross-runtime validator equality.

The pinned source explains this: [the message partial](../../../../upstream/app/views/messages/_message.html.erb) caches `[message, "presentation-v3"]`, while [the index](../../../../upstream/app/views/messages/index.html.erb) enables collection caching. The intermediate port's stronger all-user/body/boost/blob invalidation was a demonstrated difference and extra warm-query work. The current source now follows the message version policy described above. The vendored golden regression reproduces the captured stale states for both string and segmented APIs, then verifies that an API message touch refreshes them. At that stage the Chat suite passed **50 tests** and Release built without warnings/errors. The final-04 through final-06 captures below record subsequent executable validation and two further no-op corrections. The preceding 223 passing comparisons and benchmark measurements remain attached to the intermediate source/image IDs and do not establish universal Rails parity.
