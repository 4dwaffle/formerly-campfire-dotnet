# Persistence status

Prepared-command reuse now retains at most32 idle managed/native connections and256 SQL-keyed command entries per connection. Every lease remains exclusive. Bursts create extra isolated connections without a capacity wait; excess idle connections close when returned. Existing concrete Dapper.AOT call sites use a SqliteConnection/SqliteCommand-compatible adapter, so parameter/result generation is unchanged. Cached commands retain native preparation, not query results, users or permissions. Session revocation and role changes are still checked on each new request.

Commands receive the current transaction/timeout and exact current parameter names/types/values before execution. Return clears managed parameter values toDBNull and detaches the transaction. Microsoft.Data.Sqlite10.0.12 resets native statements but retains native bound values until rebinding, eviction or close; this implementation preserves that provider behavior and does not claim secret zeroing. Missing parameters raise instead of returning an earlier binding. Faulted commands are finalized, SQLite v2 automatically reprepares changed schemas, LRU eviction finalizes old commands, and explicit connection Close forces physical replacement. Multi-statement SQL occupies one command entry, potentially containing multiple native statements.

Store disposal rejects new connection rentals and drains active leases/committed callbacks before closing retained handles. Provider ClearPool/ClearAllPools no longer owns these store-held connections; store.Dispose or explicit connection.Close owns their lifetime. The writer semaphore uses only managed state and stays valid while pre-shutdown admissions unwind; no WaitHandle is allocated. Read/write lease callbacks must not return a live reader or retain a connection for later use.
